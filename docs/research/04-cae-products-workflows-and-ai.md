# 04 — CAE products, workflows, scriptability, browser FEA, and AI-driven FEA

Research note, 2026-09-05. Compiled from five parallel source sweeps (incumbent tools, Blender architecture, browser CAE, AI+FEA literature and MCP servers, V&V benchmarks). Every non-trivial claim carries a URL; items the sweeps could not confirm from a primary page are marked **not verified**. Several vendor doc servers (docs.blender.org, devtalk, code-aster.org man pages, some Autodesk/Ansys pages) returned 403/404 to the fetcher, so primary content was read from git mirrors (Blender source and manual repos, Code_Aster GitLab test sources, the public MIT Abaqus 2017 mirror, Ansys' public Verification Manual) instead.

## Executive summary

1. **"Fully scriptable" in the best incumbents means the GUI *writes* the script, not merely that a script API exists.** Abaqus/CAE appends every modelling click to `abaqus.rpy` as Python; COMSOL keeps a complete Java history inside the `.mph` and exposes it via *Save as Java/M-file*, *Record Method* and *Copy as Code*; LS-PrePost logs to `lspost.cfile`; ParaView has *Start/Stop Trace*; Salome has *Dump Study*; FreeCAD echoes Python to the console; Gmsh appends to the `.geo`. Ansys Mechanical is the cautionary case: journaling is split across Workbench (`.wbjn`) and Mechanical (Recording, which Ansys states "does not support every available API"), with APDL as a third language underneath. Structural tools common in Norway (Robot, FEM-Design, RFEM, CSi OAPI) have APIs but the GUI never writes code for you; SOFiSTiK is the text-first outlier.
2. **Verdict for us:** GUI action = script line, emitted continuously to a visible log that is copy-pasteable and replayable, is the bar. Recorded picks must be robust (Abaqus' own guide tells users to replace integer-id picks with `findAt`) — so selections should be recorded as geometric/named queries, never as internal ids.
3. **Blender is the architectural model:** one property definition (RNA) drives the widget, the Python attribute, tooltips, units, undo, animation and the file format; every button is an *operator* with declared, serializable properties; undo steps are pushed per operator (`REGISTER`+`UNDO`); *Adjust Last Operation* is "undo, then re-run with edited params"; the Info editor logs the Python for every action and property edit. Its documented failures — operators that read *context* instead of taking arguments ("context is incorrect"), modal operators, only-REGISTER-ops logged — are the things to design out from day one.
4. **Browser FEA exists but every commercial product solves server-side** (SimScale on OpenFOAM/Code_Aster, Onshape's TrueSOLID, Fusion's token-metered cloud, SkyCiv's REST API, CAEplex on FeenoX/CalculiX). Onshape's own blog is explicit that "browser CAD" means Parasolid on geometry servers with WebGL drawing triangles. Client-side solvers are small open-source projects only (FEAScript, `fea_app` Rust/WASM+WebGPU PCG, GMSH-JS, opencascade.js). No CalculiX/FEniCS/OpenSees browser build was found. A WebGPU 3D solid solver with mesh, assembly, solve and post all in the tab would be first of its kind.
5. **The AI-FEA literature is consistent:** executability ≠ correctness (FEABench: 88% executable calls, 1–2 of 15 problems within 10% error; MOOSE study: 39–40% of "repaired" cases run but solve the wrong PDE). What moves the needle: an execution/repair loop with a real retry budget (0.9% → 96.4% on FoamBench), API docs/tutorials in context (interface factuality 0.54 → 1.00), constraining routine physics to a validated schema while keeping a code escape hatch, deterministic physics gates (analytical references, convergence checks), explicit defaults, structured error returns, and geometry generated as code and checked visually/geometrically. Geometry and BCs are the weakest links; materials get hallucinated by 3 orders of magnitude without a lookup.
6. **Every popular CAE/CAD MCP server (>100 stars) is hybrid:** one `execute_code` tool plus a handful of typed inspectors (scene info, screenshot, job status). Pure-structured servers exist (FEP-Agent-Hub, one COMSOL MCP, PDE-Agents) and trade coverage for validatability. Ansys now ships official PyMAPDL/PyMechanical/PyFluent MCP servers on the same hybrid pattern.
7. **V&V should be built in, not bolted on:** NAFEMS LE1/LE10/LE11/FV32/T4, MacNeal-Harder beams, Cook's membrane, Kirsch plate, Lamé cylinder, Euler-Bernoulli cantilever modes, and manufactured-solution convergence rates give a ~15-test automated suite with published reference numbers (section 5). Two references need resolving before hard-coding: FV52 (Ansys-implied vs Abaqus-printed set) and Cook's membrane (23.9 plane-stress vs 21.520 in recent papers).

## 2. Blender's scriptability architecture (the model to copy)

Primary sources: Blender's own `doc/python_api/rst` and `source/blender` in the git mirror, and the manual/developer-docs repos on projects.blender.org (docs.blender.org itself returned 403).

### 2.1 Data API vs operators

- `bpy.data` gives direct read/write of data-blocks; `bpy.context` is "read-only" and holds the user's selection; `bpy.ops` are "tools generally accessed by the user from buttons, menu items or key shortcuts … Python can run these with its own settings" ([quickstart](https://raw.githubusercontent.com/blender/blender/main/doc/python_api/rst/info_quickstart.rst)). `bpy.types` holds RNA-generated classes; `bpy.props` declares properties for operator arguments and PropertyGroups.
- The Python console exposes `C`/`D` shortcuts and Tab autocompletion ([python_console.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/editors/python_console.rst)).

### 2.2 The Operator concept

- Every button/menu item/shortcut is an operator: a `bpy.types.Operator` subclass with `bl_idname`, `bl_label`, `bl_options`, and `bpy.props` annotations; registered with `bpy.utils.register_class`, callable as `bpy.ops.object.data_edit(prop=…)` ([info_overview](https://raw.githubusercontent.com/blender/blender/main/doc/python_api/rst/info_overview.rst)).
- Lifecycle: `poll(cls, context)` (can it run?), `execute(self, context)`, `invoke(self, context, event)` (UI entry: props dialog, file selector, `modal_handler_add`), `modal(self, context, event)` ("Grab, Rotate, Scale, and Fly-Mode are examples of modal operators"), `draw()` for the redo panel ([Operator examples](https://raw.githubusercontent.com/blender/blender/main/doc/python_api/examples/bpy.types.Operator.6.py)).
- Return values (from `rna_wm.cc`): `RUNNING_MODAL`, `CANCELLED` ("no undo entry should be pushed"), `FINISHED`, `PASS_THROUGH`, `INTERFACE` ([rna_wm.cc](https://raw.githubusercontent.com/blender/blender/main/source/blender/makesrna/intern/rna_wm.cc)).
- `bl_options`: `REGISTER` "Display in the info window and support the redo toolbar panel"; `UNDO` "Push an undo event when the operator returns FINISHED"; `UNDO_GROUPED`, `BLOCKING`, `MACRO`, `PRESET`, `INTERNAL` "Removes the operator from search results".
- **Undo is per operator:** "Any operator modifying Blender data should enable the 'UNDO' option … Otherwise, no undo step will be created, which will at best corrupt the undo stack" ([Operator.1.py](https://raw.githubusercontent.com/blender/blender/main/doc/python_api/examples/bpy.types.Operator.1.py)). In `wm_event_system.cc`: `if (op->type->flag & OPTYPE_UNDO) ED_undo_push_op(C, op)` and the Info report happens only for `OPTYPE_REGISTER` ([wm_event_system.cc](https://raw.githubusercontent.com/blender/blender/main/source/blender/windowmanager/intern/wm_event_system.cc), [undo.md](https://projects.blender.org/blender/blender-developer-docs/raw/branch/main/docs/features/core/undo.md)).
- **Adjust Last Operation (F9):** `ED_undo_operator_repeat` undoes the last step, re-runs with stored properties, and on failure redoes ([ed_undo.cc](https://raw.githubusercontent.com/blender/blender/main/source/blender/editors/undo/ed_undo.cc)). Eligibility requires both `REGISTER` and `UNDO`; `PROP_SKIP_SAVE` marks props (mouse position) not preserved across repeats; `PROP_HIDDEN` hides them from the auto-generated redo UI ([RNA_types.hh](https://raw.githubusercontent.com/blender/blender/main/source/blender/makesrna/RNA_types.hh)).
- Execution context: `bpy.ops.x.y('INVOKE_DEFAULT')` runs `invoke` (popup) instead of `execute`; menus set `layout.operator_context`.

### 2.3 RNA / DNA

- **DNA** = "a low-level system that describes the data structures stored in .blend files in a reproducible, forward- and backward-compatible manner"; the `.blend` embeds its own SDNA so files are self-describing ([dna.md](https://projects.blender.org/blender/blender-developer-docs/raw/branch/main/docs/features/core/dna.md)).
- **RNA** = "a system for defining structured data with rich metadata and runtime behavior" driving "the UI, animation system, library overrides, and the Python API (bpy)". Metadata per property: label, description (tooltip), icon, range, units, enum items, getter/setter callbacks, update functions "to notify other systems (e.g., UI refresh, dependency graph)", animation/override flags ([rna.md](https://projects.blender.org/blender/blender-developer-docs/raw/branch/main/docs/features/core/rna.md)). `PointerRNA` carries enough context "to compute rna paths or trigger updates after changes".
- Property flags carry policy: `PROP_EDITABLE`, `PROP_ANIMATABLE`, `PROP_HIDDEN`, `PROP_SKIP_SAVE`, `PROP_ENUM_FLAG`; subtypes `PROP_DISTANCE`, `PROP_ANGLE`, `PROP_UNIT_LENGTH` give unit display.
- Python classes are generated at runtime from RNA (`pyrna_srna_Subtype`); every object exposes `bl_rna`/`rna_type`, `bl_rna.properties`, `path_from_id()`, `path_resolve()`, `keyframe_insert()`, `driver_add()`, `is_property_set()` ([bpy_rna.cc](https://raw.githubusercontent.com/blender/blender/main/source/blender/python/intern/bpy_rna.cc)).
- UI draws from RNA: `UILayout.prop(data, property)` "Exposes an RNA item and places it into the layout"; `UILayout.operator(operator)` "Places a button into the layout to call an Operator" ([rna_ui_api.cc](https://raw.githubusercontent.com/blender/blender/main/source/blender/makesrna/intern/rna_ui_api.cc)). One `RNA_def_property` therefore powers the widget, the Python attribute, keyframing, overrides and (via DNA) the file format.

### 2.4 Discoverability

- **Info editor** "logs the executed operators as well as errors, warnings, and informational messages"; entries copy-paste into scripts. Caveat: "this only reports operators with the REGISTER option enabled"; `--debug-wm` logs everything ([info_editor.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/editors/info_editor.rst), [tips](https://raw.githubusercontent.com/blender/blender/main/doc/python_api/rst/info_tips_and_tricks.rst)).
- **Property edits are logged too:** `apply_but_autokey()` calls `WM_prop_pystring_assign` and reports `RPT_PROPERTY` — "make a little report about what we've done!" ([interface_handlers.cc](https://raw.githubusercontent.com/blender/blender/main/source/blender/editors/interface/interface_handlers.cc)).
- Preferences: "Python Tooltips — Displays a property's Python information below the tooltip"; "Developer Extras" enables Operator Search, "Copy Python Command", "Edit Source", "Online Python Reference" ([interface.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/editors/preferences/interface.rst)). Ctrl-C over a button copies its `bpy.ops` command.
- Button context menu: "Copy Data Path", "Copy Full Data Path … including any needed context information", "Copy As New Driver", "Assign Shortcut" ([menus.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/interface/controls/buttons/menus.rst)). Text editor templates and Register-on-load; console "Copy as Script".

### 2.5 Add-ons and Extensions

- "Blender modules loaded at startup require `register()` and `unregister()` functions. These are the only functions that Blender calls from your code" ([info_overview](https://raw.githubusercontent.com/blender/blender/main/doc/python_api/rst/info_overview.rst)). Menus extended by appending a draw function; keymaps via `wm.keyconfigs.addon.keymaps.new` ([addon_tutorial.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/advanced/scripting/addon_tutorial.rst)).
- Extensions (4.2+): `blender_manifest.toml` replaces `bl_info`; declared permissions "files, network, clipboard, camera, microphone" each with a justification; bundled wheels; namespaced `bl_ext.{repo}.{id}` ([getting_started.rst](https://projects.blender.org/blender/blender-manual/raw/branch/main/manual/advanced/extensions/getting_started.rst)).

### 2.6 Where Blender violates "everything through the same API"

Blender's own gotchas page is the sharpest critic ([info_gotchas_operators.rst](https://raw.githubusercontent.com/blender/blender/main/doc/python_api/rst/info_gotchas_operators.rst)):

- Operators "Can't pass data such as objects, meshes or materials to operate on"; "The return value from calling an operator is the success"; "poll function can fail where an API function would raise an exception".
- `RuntimeError: Operator bpy.ops.action.clean.poll() failed, context is incorrect` — operators read active area/selection from context; remedy is `Context.temp_override(window=, area=, region=, …)` ([bpy_rna_context.cc](https://raw.githubusercontent.com/blender/blender/main/source/blender/python/intern/bpy_rna_context.cc)). `poll_message_set` can explain a failed poll.
- Modal operators can't be meaningfully called from a script; the Info log shows only the final `bpy.ops.transform.translate(value=…)`, not the interaction. Only `REGISTER` operators are logged; view navigation is invisible.
- Data-API gotchas: stale evaluated data until `view_layer.update()`; Python wrappers of freed data after undo can cause "invalid memory access" ([gotchas_internal_data](https://raw.githubusercontent.com/blender/blender/main/doc/python_api/rst/info_gotchas_internal_data_and_python_objects.rst)).
- `bpy.data` edits outside an `UNDO` operator push no undo step; a `CANCELLED` return after partial edits corrupts the stack.
- "bpy.ops is slower than the data API" and the devtalk "operators need context" criticism: widely repeated but **not verified** from primary docs here (devtalk 403).

### 2.7 Blender-MCP and relatives

- [ahujasid/blender-mcp](https://github.com/ahujasid/blender-mcp) (~27k stars, MIT): an `addon.py` TCP server on `localhost:9876` (JSON `{"type","params"}`) plus a Python MCP server. Client threads enqueue; a `bpy.app.timers` callback drains the queue on the main thread every 0.05 s ("bpy access happens here, on the main thread") ([addon.py](https://raw.githubusercontent.com/ahujasid/blender-mcp/main/addon.py)).
- Tools: `get_scene_info`, `get_object_info`, `get_viewport_screenshot`, `execute_blender_code` (`exec(code, {"bpy": bpy})`, stdout captured, no sandbox — README: "ALWAYS save your work"; `BLENDER_MCP_SAFE_MODE=1` blocks file/network), plus PolyHaven/Sketchfab/Poly Pizza/Hyper3D/Hunyuan3D asset tools ([server.py](https://raw.githubusercontent.com/ahujasid/blender-mcp/main/src/blender_mcp/server.py)). An `asset_creation_strategy` prompt says to prefer asset libraries and "Only fall back to scripting when" they are disabled.
- Design choice: a few read-only structured inspectors + one universal code executor; all mutation goes through arbitrary Python, relying on bpy being complete and discoverable.
- Relatives: [gd3kr/BlenderGPT](https://github.com/gd3kr/BlenderGPT) (2023, NL → GPT-4 → `exec`), [virtualdmns/blender-gpt](https://github.com/virtualdmns/blender-gpt); the `blender-mcp` GitHub topic (~23 repos) includes blender-mcp-pro ("100+ tools", structured per-feature) ([topic](https://github.com/topics/blender-mcp)).

### 3.3 Verdict: who solves where, and what would be first

- **Server-side: every commercial product.** Onshape is the clearest documented case that browser CAD still means server compute. The only commercial products doing GPU physics on the user's machine are desktop: Ansys Discovery (CUDA only) and nTop (implicit modelling, not FEA).
- **Client-side: all open-source, all small.** Building blocks exist (GMSH-JS for meshing, opencascade.js for B-rep, `fea_app` for a WebGPU PCG kernel), but no production-grade 3D solid-mechanics solver runs in the browser.
- **A WebGPU client-side FEA tool would be first at:** (1) 3D solid FEA (tet/hex, real BCs, stress/modal) with mesh → assembly → sparse solve → post entirely on the user's GPU, zero server compute; (2) zero-cost, offline-capable browser FEA (every commercial browser tool meters server compute); (3) Discovery-Live-style interactive GPU physics that is vendor-neutral (WebGPU on Apple/AMD/Intel/NVIDIA); (4) combining implicit/SDF GPU modelling with GPU FEA in one tab. Not first at: browser CAD kernel, browser meshing, JS FEM as such, WebGPU PCG.

### 4.5 What the literature says LLMs need

1. **An execution feedback loop with a real repair budget.** FoamBench 0.9% (R=0) → 71.8% (R≤2) → 96.4% (R≤10) ([2609.03718](https://arxiv.org/html/2609.03718)); Foam-Agent reviewer node 48% → 86% ([2509.18178](https://arxiv.org/html/2509.18178v1)); FEABench multi-turn 0.62 → 0.88 executability.
2. **API docs and worked examples in context, not memorised.** FEABench PhyDoc: interface factuality 0.54 → 1.00; tutorials the "strongest single intervention" (80.9 → 96.4%); OpenFOAMGPT 1/6 → 6/6 with RAG; undocumented functions are "effectively opaque to the agent" ([2603.00214](https://arxiv.org/html/2603.00214)).
3. **Executability is not correctness — verify physics separately.** 39–40% of MOOSE cases run but solve the wrong PDE; ChatCFD 82.1% executes vs 68.1% faithful; FEABench 88% executable, 1–2/15 correct; MechAgents' von-Mises-for-σxy.
4. **Reference/analytical checks and convergence tests as gates.** PDE-Agents verifies O(h²); CFDLLMBench scores mesh-refinement convergence; FEP-Agent-Hub ships physics gates; PDEAgent-Bench pass rates collapse once accuracy is enforced.
5. **Constrain routine physics to a validated schema; keep a code escape hatch.** JSON → deterministic templates gave 100% valid parses and <1% error ([2606.10928](https://arxiv.org/html/2606.10928)); PDE-Agents slot-filling 97.8%; VFEAgent keeps a template fallback; every popular MCP server keeps `execute_code`.
6. **Validate BCs, materials and units before solving.** Schema checks for rigid-body suppression and Poisson ratio; pure-Neumann failures; 900–2,080× material hallucinations without a knowledge graph; FEABench selection-dimension mismatches.
7. **Geometry is the weakest link; generate it as code and check it geometrically/visually.** FEABench cylinder cross-sections; multi-body Gmsh failures ([2503.18178](https://arxiv.org/abs/2503.18178)); OpenFOAMGPT's bad `blockMeshDict`; CADCodeVerify render-and-ask; Jarvis-Onshape bounding-box/mass diffs per feature.
8. **Actionable, structured error returns instead of raw logs.** CAX-Agent maps error classes to patches; Foam-Agent formalises log → {message, location, severity}; Jarvis returns `{ok, error_message, hints}`; FEP-Agent-Hub returns `BLOCKED` rather than fabricating.
9. **Make defaults explicit.** FEABench false positives from a default 293.15 K export; JutulGPT: "a choice that was never made cannot appear in an assumption log".
10. **Guard the API surface against hallucinated/unsafe calls.** VFEAgent: 30% API hallucination, 25% unsafe state ops, 45% forgetting `job.submit()`, fixed by AST preflight; comsol-mcp only accepts `model.*` lines; pyfluent-mcp `validate_code` before `run_code`.
11. **Independent, deterministic critics beat self-reflection.** Critic agent caught the zero-force result; rebuttal agents agreed 85–92% of the time ([2408.13406](https://arxiv.org/abs/2408.13406)); scripted self-reflection moved nothing on FoamBench.
12. **Harness owns control flow; one strong-model agent suffices.** "The orchestrator—not the LLM—owns retry budgets" ([2605.15218](https://arxiv.org/html/2605.15218)); a single Claude Opus 4.6 agent with shell+file tools beat all multi-agent CFD systems ([2609.03718](https://arxiv.org/abs/2609.03718)).

### 5.4 Mesh-convergence methodology and pathologies

- **Richardson / GCI (Roache):** observed order p = ln[(f₃−f₂)/(f₂−f₁)]/ln r; extrapolated f₀ = f₁ + (f₁−f₂)/(rᵖ−1); GCI = Fs|ε|/(rᵖ−1) with Fs=3.0 (two grids) / 1.25 (three+); asymptotic-range check GCI₂₃/(rᵖ·GCI₁₂) ≈ 1 ([NASA NPARC](https://www.grc.nasa.gov/www/wind/valid/tutorial/spatconv.html)). ASME V&V 20-2009 (R2021) codifies this (stable URL **not verified**).
- **Expected rates** for smooth solutions with degree-p elements: displacement/L2 O(h^{p+1}), energy/H1 O(h^p) (deal.II step-7 tables). Point stresses converge slower than global norms; re-entrant corners (Cook's, plate-with-hole edges) cap the rate at the singularity strength.
- **How commercial tools present it:** Ansys Mechanical "Convergence" object — h-adaptive loops, Zienkiewicz-Zhu error, default allowable change 20%, refinement depth 0–3 ([docs](https://ansyshelp.ansys.com/public/Views/Secured/corp/v251/en/wb_sim/ds_Convergence.html)); SimScale publishes mesh-case tables vs reference with % error (LE10 page).
- **Pathologies to test against** ([Abaqus solid elements](https://abaqus-docs.mit.edu/2017/English/SIMACAEELMRefMap/simaelm-c-solidcont.htm)): shear locking of fully-integrated first-order elements in bending ("parasitic shear") → MacNeal-Harder straight beam on a 1×6 Q4/tet mesh; volumetric locking as ν→0.5 (checkerboard pressure) → thick cylinder at ν=0.49/0.499/0.4999 and Cook's at ν=0.499999975; hourglassing of reduced-integration elements → point-loaded reduced-integration cantilever; distortion → the 0/15/30/45° skewed-mesh cantilever variants. SimScale's LE10 data (1st-order hex, 216 nodes, −29%) is a ready-made warning.

## 6. What a browser-based, AI-first FEA editor should learn from all this

1. **One property schema, many consumers (Blender RNA).** Define each model property once — id, type, label, tooltip, unit, range, default, editable/hidden flags, update hook — and generate the widget, the script attribute, serialization, undo and introspection from it. Introspection (`bl_rna.properties` equivalent) is what makes autocomplete, docs-in-context and LLM use possible.
2. **Data API for state, operators for actions.** `model.materials["steel"].E = 210e9` for state; `ops.mesh.refine(target_size=0.01)` for actions with declared, serializable parameters. Operators return status; the results live in the model.
3. **Never let operators read hidden context.** Blender's biggest regret is "context is incorrect". Selection, active view and target objects are explicit arguments with named/geometric selectors (the FEA equivalent of Abaqus' `findAt` advice) — never internal ids.
4. **Undo = operator boundary; Adjust Last Operation = undo + re-run.** Push one step on `FINISHED`, none on `CANCELLED`; store the parameter set so the redo panel is free.
5. **The GUI writes the script, continuously and visibly.** Every click emits `ops.x.y(args)`, every widget edit emits `path.prop = value`, into an Info log that is copy-pasteable and replayable. Log everything (not just "REGISTER" operators); interactive drags end by emitting the non-interactive call with final values. This log is the tutorial, the macro recorder, and the LLM's few-shot examples — it is also how Abaqus, COMSOL, LS-PrePost, ParaView and FreeCAD earned "fully scriptable".
6. **Discoverability is cheap:** Python tooltips, Copy Data Path / Copy Command, a console with `C`/`D`-style shortcuts and Tab completion, script templates.
7. **LLM bridge = hybrid, like every MCP server that got traction:** a few read-only inspectors (model tree, screenshot, job status, result probes) plus one `execute_code`, run on the main thread from a queue with an optional safe mode; add `validate_code`/AST preflight (VFEAgent found 45%/30%/25% of Abaqus-script failures were lifecycle, API-hallucination and unsafe-state errors). Add structured per-action tools only where the code path is unsafe or the API is undiscoverable.
8. **Constrain routine physics to a validated schema, keep the escape hatch.** Linear static / steady heat / modal on catalog geometry can be a slot-filled schema that validates units, positive constants, Poisson ratio, rigid-body suppression and BC dimensionality before solving (2606.10928, PDE-Agents). Free-form code for the long tail.
9. **Make executability ≠ correctness visible in the product.** Ship the section-5 suite as CI and as in-app "check against reference" buttons; show mesh-convergence (Richardson/GCI) as a first-class result; flag defaults that were never set (FEABench's 293.15 K false positive, JutulGPT's assumption log).
10. **Return structured, actionable errors** `{ok, error_class, location, hints}` rather than raw logs; a disabled action should say why (`poll_message_set`).
11. **Geometry as code, checked geometrically.** Geometry is where agents fail most; emit it as a script (Gmsh/OCC-style), and return bounding boxes, volumes, mass and a render after each feature (Jarvis-Onshape, CADCodeVerify).
12. **Materials from a lookup, never from the model's memory** (900–2,080× errors without a knowledge graph).
13. **Docs and examples travel with the API.** Every operator and property carries its docstring, unit and an example call; expose them as an MCP resource — tutorials in context were the single strongest intervention in the 2026 harness study.
14. **Client-side WebGPU is genuinely uncontested.** Every commercial browser tool meters server compute; only tiny open-source projects solve in the tab. Zero-cost, offline, vendor-neutral GPU FEA is the differentiator; the building blocks (GMSH-JS, opencascade.js, WebGPU PCG) already exist.
